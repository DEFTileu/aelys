# Общие правила UI/UX-целей Aelys

1. Прочти AGENTS.md, обязательные проектные документы и docs/UX_RESEARCH.md; выбери только указанный в цели вертикальный срез IMPLEMENTATION_PLAN. Явный запрос владельца на переработку внутренних экранов разрешает UI-дизайн в этом объёме.
2. Используй установленные `icon-system`, `ui-ux-pro-max` и применимый `frontend-design`. Прочти их SKILL.md; рекомендации проверяй по сценарию и текущему стеку React/TS, не устанавливай новый UI-framework без необходимости. Следуй доступности и progressive disclosure. Референсы изучай по официальным источникам; копирование чужого интерфейса/логотипов не требуется.
3. Сохрани все существующие незакоммиченные изменения, single-owner session, реальные API, BYOK, Telegram Policy Engine, точную DecimalMoney и приватность Mac. Не сбрасывай БД/аккаунт. Дизайн и поведение должны работать на фактических данных; никаких mock-success, искусственных статистик и декоративных активных кнопок.
4. Сначала короткий аудит → конкретный вариант → рабочая реализация. Обычные обратимые решения принимай самостоятельно; не останавливайся на плане/макете и не проси повторного разрешения на уже заказанный scope. Пользовательские OPEN-решения не превращай в утверждённые. До миграций при изменении сущностей обнови типизированный контракт, миграции и релевантные проверки.
5. Перетаскивание/resize работают напрямую. Добавь также pointer-альтернативу через меню/форму и клавиатуру; не делай drag единственным способом. Сохрани meaningful labels, visible focus, Escape/Enter, возврат фокуса, контраст и reduced-motion. Горячие клавиши не срабатывают внутри ввода/редактора. Проверь viewport 390, 768 и 1440 CSS px.
6. Локальные пользовательские изменения фиксируй durable до попытки sync, если используешь существующий offline-контракт. Не обещай offline-write там, где он не поддержан; не включай слепой replay без доказанного server idempotency. Loading/empty/error/offline/conflict показывай раздельно. Ошибка не должна терять введённые данные.
7. Проверь существующие и новые существенные пользовательские сценарии, web/shared typecheck и build. Backend/tests/mypy/Ruff/Bandit и OpenAPI — если менялся backend. Открой локальную версию и пройди сценарий в браузере; скриншоты + точные результаты в отчёт. Чужие тестовые аккаунты/секреты не создавай в личной БД; используй изолированную базу для fixtures.
8. Разрешено до шести субагентов с непересекающимися файлами. Не создавать отдельные пользовательские чаты вместо субагентов; не запускать несколько целей параллельно через один Git index. Git-проверки и явный staging по docs/GIT_WORKFLOW.md; не коммитить чужую работу.
9. Заверши именно выбранную цель, оставь локальную версию функционально доступной. Отчёт: что изменилось, файлы, commands/tests, скриншот, ограничения, следующая зависимая цель. Если внешний credential отсутствует, реализуй всё проверяемое и назови конкретный оставшийся live-check; не заявляй внешнее подключение проверенным.
