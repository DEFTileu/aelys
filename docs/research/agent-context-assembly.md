# Сборка контекста одного вызова модели

Срез задачи 2 фазы 4 из IMPLEMENTATION_PLAN (оркестрация и лимиты). База реализации — `455a05d`. Исполняемые точки входа — Web AI Chat и существующий AIExecutionService. Все прогоны используют синтетические данные. Схема БД и тексты системных промптов сохраняются.

## Основания

Anthropic описывает повторный отбор данных на каждой итерации агента и выборку подробностей по запросу. Для Aelys это означает, что после tool call нужно заново учитывать реальный набор схем, аргументы и результат, а старую переписку можно убрать целыми ходами. Конкретные веса, порядок и ограничения ниже — решения этого среза. [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

Спецификация MCP различает описания инструментов и возвращённые данные, требует проверки входов, контроля доступа и осторожности с аннотациями сервера. В Aelys это поддерживает существующее разделение между ToolRegistry/Policy Engine и текстом, который видит модель. [MCP Tools, версия 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

## Один запрос от источника до транспорта

1. Канал связывает вызов с аутентифицированным владельцем и конкретным разговором, интеграцией или устройством. Web проверяет владельца разговора; запрос истории дополнительно соединяет сообщения с разговором владельца. Из хранилища разрешены роли user/assistant. Для истории действуют фильтры незавершённых запросов и устаревшей памяти.
2. Компоновщики возвращают существующий ChatMessage. ContextTrust различает серверную инструкцию, диалог и свидетельство. Для KB, памяти и инструментов ContextSource требует untrusted. Старые компоновщики совместимы через флаг untrusted. История несёт ID записи до границы транспорта. KB несёт note_id, версию и диапазон цитаты, память — ID и версию, результат инструмента — ID соответствующего вызова. Эти поля задаёт код, содержимое сообщений их не назначает.
3. После выбора ModelSpec сервис проверяет исходный набор данных на egress **до сокращения**. Даже секрет в вытесняемой истории блокирует передачу. Маркером служит существующая граница UntrustedData с фиксированным именем источника; внешнее сообщение с ролью system понижается до user. Адаптеры независимо проверяют собранный wire payload, в том числе на совпадение с ключом провайдера. Фильтры обнаруживают известные формы, а права задаёт PermissionContext, проверяемый при вызове инструмента.
4. Обе ветви — complete и stream_sse — вызывают fit_context. В окно входят примерный объём текста после ограждения, схемы текущего шага, аргументы вызовов, их результаты, накладные расходы и резерв ответа. Для Claude резерв учитывает предпочтение адаптера в 16k с ограничением в четверть окна для маленьких моделей и нижней границей по запросу вызывающего кода. Этот резерв передаётся в max_tokens. Старые ходы выбираются с конца до первого, который не помещается. Текущий запрос, инструкции, выбранные источники и пары вызов/результат обязательны. При переполнении обязательной части сервис прерывает отправку через ModelUnavailable.
5. run_tool_turn проверяет отмену, доступный бюджет Decimal и версии памяти перед очередной итерацией. Успешный remember добавляет зависимость от созданной версии. Ответ модели с вызовами и все результаты этого шага получают общие зависимости; при отзыве удаляется вся зависимая группа. Повторный ID в рамках того же turn не выполняет обработчик повторно. На следующем шаге учитываются новые сообщения и фактически предложенные схемы. Лимиты количества шагов и учёт стоимости остаются в общем цикле.
6. Web хранит версии памяти, влияющие на ответ, в существующем source_refs_json. Ссылки памяти скрыты из публичного списка цитат. В tool-ветви ссылки также привязаны к исходному вопросу. История остаётся видимой владельцу; следующий запрос заново проверяет актуальность. Ссылки консервативно включают историю, отобранную до финального сокращения.

## Проверки и ограничения

При переносе на `ab80544` сохранены фильтрация истории по связям вопроса и ответа,
пошаговая загрузка инструментов и изолированная история групп. Пары вызовов и результатов
наследуют ссылки на память из ответа `read_chat_history`, чтобы отзыв исключал весь
зависимый обмен. Первичный выбор модели в личном Telegram учитывает обязательный ввод.
Старая переписка подгоняется под окно модели на границе провайдера.

- Новый тест провёл 60 синтетических пар сообщений через complete и SSE при окне 1500. Обе ветви оставили один и тот же свежий суффикс из целых пар; конфликтующая внешняя «инструкция» попала в user evidence. Секрет в самом старом сообщении заблокировал следующий вызов.
- Web-тест проходит через ASGI и настоящий сериализатор Claude с подменённым HTTP-транспортом: из 35 длинных сообщений остаются последние, чужой разговор не попадает в payload, чужой owner не получает строк из выборки. Другой тест выполняет настоящий remember через ToolRegistry, отзывает факт и проверяет следующий запрос на отсутствие маркера.
- Тест бюджета подставляет слишком большую схему или результат во втором шаге и получает ModelUnavailable. test_shared_tool_turn проверяет два ответа с одним ID и ровно одно выполнение write; test_telegram_memory проверяет отзыв между шагами. Права проверяются существующими тестами policy, secretary и owner web search.
- test_companion_channel проверяет отзыв во время жизни сокета. В отдельном снимке неизменённого ab80544 прогнаны test_telegram_guest, test_telegram_group_memory, test_companion_voice и test_read_chat_history. Это исходная проверка отсутствующих каналов. После переноса нужны повторные прогоны по объединённому коду.
- Локальный Rust session_indexing работает с временными файлами; runtime_contracts проверяет проекцию метаданных без content, prompt, embedding, локальных путей и идентификаторов. Python-тесты sync и разрешённых полей ресурса проверяют вход облачной части. Новый сборщик не имеет адаптера для файловых сессий, локального индекса или embeddings. Эти проверки охватывают штатные пути. Произвольный вручную вставленный текст классифицировать как CLI-транскрипт по содержанию невозможно.
- Подсчёт текстовых токенов — детерминированная оценка UTF-8 с поправкой на не-ASCII. Бинарные вложения ограничиваются существующими правилами канала; фактическая токенизация изображений, PDF, внутренних поисковых инструментов и framing провайдера не измеряется. Переполнение после реальной токенизации возможно. OPEN — калибровка на моделях и точный подсчёт. Первичный routing некоторых каналов ещё может отклонить большой запрос до сокращения.
- Отзыв проверяется перед сборкой следующего запроса. Уже отправленные байты, старые ответы без ссылок на факты и видимая пользователю история ретроспективно не очищаются. Длинный required tool result может завершить ход после выполненного действия. Идемпотентность одного call_id ограничена текущим запуском; повтор между запусками зависит от существующих доменных ключей. Переход к меньшим страницам результатов и прозрачная частичная выдача остаются точками миграции.

## Воспроизведение

Из корня checkout для локального индекса и экспортируемой схемы:

```sh
cargo test --manifest-path apps/runtime/Cargo.toml --test session_indexing
cargo test --manifest-path apps/runtime/Cargo.toml --test runtime_contracts metadata_projection_has_no_local_content_fields
```

Из backend для синтетических HTTP, DB, provider и sync контрактов:

```sh
uv sync --frozen --extra test --extra quality
.venv/bin/python -m pytest -q tests/ai_automation tests/test_telegram_memory.py \
  tests/test_telegram_context_sessions.py tests/test_companion_access.py \
  tests/test_companion_channel.py tests/test_memory_secretary_boundary.py \
  tests/sync/test_sync_engine.py tests/domains/test_domain_apis.py::test_agent_session_resource_metadata_is_allowlisted
```

Для воспроизведения исходной проверки предыдущего стека выполнить в его каталоге backend:

```sh
python -m pytest -q tests/test_telegram_guest.py tests/test_telegram_group_memory.py \
  tests/test_companion_voice.py tests/test_read_chat_history.py
```
