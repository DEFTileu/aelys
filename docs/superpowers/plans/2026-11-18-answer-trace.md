# «Как я ответил»: мини-приложение Telegram и чтение истории чата

**Статус:** задание владельца, 2026-11-18. Кода нет. Это единственный источник
требований для ветки `codex/answer-trace`; план исполнения дописать ниже, в
раздел «План исполнения», и работать по нему.

## Что хочет владелец

Под ответом личного бота в Telegram — ссылка. Она открывает мини-приложение,
где видно, как получился ответ: сколько работал, какие шаги сделал, что искал
и что нашёл. Плюс ассистент сам читает историю своего чата с владельцем, когда
вопрос на неё опирается, и это тоже видно как шаг.

Образец экрана (описание референсов владельца):

- строка «Работал 8 с», под ней список шагов: «читал чат за 24 часа»,
  «искал „…“»;
- тап по шагу открывает шторку снизу с деталями шага;
- у шага поиска — список найденных страниц: заголовок и домен, до 10 строк;
- внизу ответа счётчик «Источники N».

Рассуждений модели на экране нет: только шаги, запросы и источники.

## Что уже есть в коде (проверено на `770b28c5`)

- Шаги запуска пишутся в `AIRunEvent`: `ai.run.started`, `ai.tool.requested`,
  `ai.tool.approved`, `ai.tool.result`, `ai.run.completed`
  (`backend/app/ai/turn.py`, `_persist_event` в `backend/app/ai/api.py`).
- Web-чат уже рисует шаги из этих событий: `RunStep` в
  `apps/web/src/views/ai/useAi.tsx`.
- У `web_search` в событие попадают только запрос и статус. Источники — строки
  URL без заголовков, не больше пяти, дописываются в текст ответа.
- Мини-приложения и входа по `initData` в проекте нет.
- Telegram-ответ и статус `completed` сохраняются одним коммитом в
  `backend/app/integrations/telegram_personal_dialogue.py`; текст уходит
  владельцу через `_send_owner`.
- Инструменты личного ассистента: `list_tasks`, `create_task`, `update_task`,
  `complete_task`, `search_notes`, `read_note`, `create_note`, `read_calendar`,
  `create_event`, `create_reminder`, `search_knowledge`, `remember`, `forget`,
  `web_search`. Чтения истории чата нет.
- История для модели собирается в `conversation_history`
  (`backend/app/ai/chat_support.py`): 20 последних сообщений текущей беседы.
  После 6 часов тишины Telegram начинает новую беседу
  (`telegram_personal_queue.py`), прошлую бот не видит.

## Часть 1. Мини-приложение

1. **Ссылка.** Отдельной строкой под текстом ответа:
   `https://t.me/<bot_username>?startapp=run__<id запуска>`. Идентификатор —
   сам id запуска, новой таблицы не заводить: доступ решает проверка
   `initData`, а не секретность ссылки. Ссылка добавляется только в
   отправляемое сообщение; в сохранённый `AIMessage` и в историю модели она не
   попадает. Превью ссылки отключить.
2. **Сверить с документацией Telegram** и записать в план: допустимые символы и
   длину `startapp`; что включить в BotFather (Main Mini App); как параметр
   приходит в приложение; алгоритм проверки `initData`.
3. **Endpoint.** Один, только чтение, один запуск. Вход только по `initData`:
   подпись токеном бота, срок `auth_date` (PROPOSED 1 час), `user.id` равен
   `owner_telegram_id` интеграции, запуск принадлежит этому владельцу. Чужой и
   несуществующий запуск дают одинаковый 404. В `API_ALLOWLIST` нативного
   транспорта маршрут не добавлять: его зовёт только мини-приложение.
4. **Что отдаёт endpoint:** длительность, модель, шаги (вид, подпись, запрос,
   статус, источники), итоговые источники, число сообщений истории, id и
   тексты использованных фактов памяти (только актуальных версий).
   Не отдаёт: системную инструкцию, ключи, рассуждения модели, данные
   Business-канала. Размер деталей шага ограничить.
5. **Источники поиска.** В событие результата `web_search` добавить список
   `{url, title}`, до 10. Проверить, отдают ли адаптеры claude и openrouter
   заголовки. Лимит поисков, фильтр ссылок и запрет записи после поиска не
   менять.
6. **Экран.** Где жить — решить фактом: маршрут в `apps/web` с
   переиспользованием `RunStep` или одна статическая страница от backend;
   нужен публичный HTTPS. Цвета из темы Telegram. Иконки сайтов с чужих
   серверов не грузить: буква домена вместо иконки. Без новых зависимостей.

## Часть 2. Инструмент `read_chat_history` (отдельная ветка после части 1)

- Читает только диалог владельца с этим ботом, включая прошлые беседы до
  смены через 6 часов. Беседы Web-чата и переписки секретаря не трогать.
  Связь беседы с Telegram брать из данных, а не из названия беседы.
- Аргументы: период или «раньше такого-то сообщения», лимит; чтение назад
  постранично.
- Отбор тот же, что в `conversation_history`: без вопросов с незавершёнными
  запусками и без сообщений со ссылками на устаревшие факты памяти. Удалённый
  факт не должен вернуться через историю. Логику переиспользовать, не
  копировать.
- Результат помечать `untrusted`. Запрет записи после чтения не вводить:
  «создай задачу из вчерашнего разговора» должно работать, право на запись
  даёт текущая просьба владельца.
- В событие шага писать период и число сообщений, без текстов.
- В инструкции ассистента одна строка: историю читать, только когда вопрос на
  неё опирается.

## Границы

- Policy Engine не менять и не обходить. Business-канал не трогать.
- Секреты не попадают во фронтенд, логи и модель.
- Миграции, деплой и живые запросы к модели — только с разрешения владельца.
- Решения, помеченные PROPOSED, остаются предложениями до его ответа.
- Репозиторий публичный: имя бота, id владельца и токены в файлы не писать.

## Тесты

- `initData`: верная подпись, подделанная, просроченная, другой пользователь.
- Чужой запуск и несуществующий запуск — одинаковый 404.
- В ответе endpoint нет запрещённых полей.
- У события поиска есть заголовки источников.
- Ссылка есть в отправленном сообщении и отсутствует в сохранённом `AIMessage`.
- `read_chat_history`: видит прошлую беседу; не видит Web-чат и переписки
  секретаря; не возвращает сообщение с устаревшим фактом памяти; после чтения
  запись задачи проходит.

**Scope:** Phase 4 / task 4, Search + provenance + redaction. Часть 1 —
`codex/answer-trace`; часть 2 — новая `codex/answer-trace-history` от проверенного
коммита части 1. Worktree изолирована; исходный checkout не меняется.

**Решения владельца в чате 2026-11-18:** срок initData утверждён — 3600 секунд;
недоступную GPT-6.1 Terra заменить GPT-6.2 Sol. Реализация GPT-6.1 Sol проверяется
GPT-6.2 Sol и наоборот. Коммиты делает только ведущий агент.

**Архитектура:** статическая страница backend `/telegram/answer-trace` и один
JSON GET `/api/v1/telegram/answer-trace/{run_id}`. Факт выбора: web App находится
за AuthGate, RunStep — модель состояния, а не самостоятельный экран. Отдельная
страница избегает загрузки owner shell и native transport, использует тот же
HTTPS origin и не требует зависимостей. Страница публична, данные — только после
initData в заголовке `Authorization: tma <initData>`, никогда в URL/cookie/storage.

**Telegram:** проверено по https://core.telegram.org/bots/webapps и
https://core.telegram.org/api/links#main-mini-app-links (2026-11-18).
Main Mini App открывается через `?startapp=run__<UUID>`; параметр приходит как
`start_param` в initData и `tgWebAppStartParam`. UUID с префиксом — 41 ASCII символ
из букв, цифр, `_` и `-`; общий предел startapp дополнительно сверяется перед
финальным отчётом. Неподписанный параметр выбирает ресурс, но не даёт доступ.
BotFather: `/mybots` → выбрать бота → Bot Settings → Configure Mini App → Enable
Mini App; указать публичный HTTPS URL страницы. Это действие выполняет владелец.
Подпись: разобрать query string, исключить hash, остальные поля сортировать по
ключу и соединить `key=value` через LF; secret = HMAC-SHA256(key=WebAppData,
message=bot_token), expected = HMAC-SHA256(secret, data_check_string); сравнить
constant-time. Затем проверить auth_date (не будущее, возраст ≤3600), user.id и
принадлежность личного запуска интеграции. Дубликаты и некорректные поля отклонять.
