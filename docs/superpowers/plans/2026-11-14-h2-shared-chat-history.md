**Этап:** Phase 4, AI harness; сначала красный Web-тест, затем отдельная реализация после согласования.
**Цель:** перенести общий отбор истории из Telegram в `backend/app/ai/chat_support.py` для Web и личного Telegram.
**Границы:** без миграций, новых зависимостей, деплоя, Business, сжатия, токен-лимитов и векторного поиска; Policy Engine и тексты инструкций не менять.

## Факты и открытые вопросы

- Красный тест `backend/tests/ai_automation/test_web_unanswered_history.py`: реальный Web API сохраняет вопрос, провайдер падает; следующий запрос модели ошибочно содержит оба вопроса. Команда запуска ниже; получен `1 failed` по ожидаемому сравнению.
- Web Retry после ошибки создаёт новый run и новое сообщение с тем же текстом; regenerate создаёт новый run по старому вопросу, а скрытие прежних строк происходит только в UI. PATCH сообщения поддерживает лишь feedback ответа, не редактирование вопроса. Два вопроса подряд в БД законны.
- Web UI блокирует параллельную отправку внутри одного экземпляра (`busy.current`), но API не сериализует runs одной беседы: устройства/вкладки могут запускать их параллельно, а ответы приходить не по порядку.
- `AIRun.prompt_message_id` связывает запуск с вопросом, но сохранённый ответ не содержит run/message ID; соседство ролей — эвристика Telegram `bf0343a`, а не доказанная связь ответа с вопросом. Владелец утвердил фильтр по AIRun: completed или отсутствие запусков сохраняет вопрос; соседство не используется. Ответы по-прежнему не связаны с run.
- `AIMessage.source_refs_json` есть в обоих каналах; Telegram записывает `owner_memory_fact` (id/version) в вопрос/ответ, Web при обычном чате факты в этих refs не записывает; старые Web-ответы проверить на устаревание невозможно. Запись refs в Web — отдельное поведение и требует обсуждения, не выдумывать provenance.
- Web выбирает `created_at DESC`, Telegram — `created_at DESC, id DESC`; PROPOSED общий `(created_at, id)` и срез строго до текущего `(created_at, id)` с включением текущего один раз. UUID не доказывает реальный порядок при одинаковом timestamp; тесты tie и позднего ответа обязательны.
- Telegram сначала отбрасывает сообщения с устаревшими refs, затем фильтрует вопросы по статусу запуска; это может изменить соседство. Сохранить порядок операций и сравнить поведение; пользовательский текущий вопрос не терять при устаревшем ref.
- PROPOSED: параметр глубины сохраняет прежние значения Web 100 и Telegram 20, включая текущий вопрос; ограничение применяется до фильтрации. Различия на границе среза не считать общей историей.
- PROPOSED: вставлять свежие факты памяти непосредственно перед текущим вопросом, вопрос последним; Web уже так делает, Telegram сейчас добавляет память после вопроса. Порядок влияет на последний user-turn, кэширование и поведение провайдера; отдельно проверить quote/media и не менять их сбор без согласования.
- Перенос `untrusted` и валидных `memory_refs` из Telegram меняет текущую Web-сериализацию исторических сообщений с такими refs; проверить реальные payload адаптеров и не ослаблять ограничения доверия.
