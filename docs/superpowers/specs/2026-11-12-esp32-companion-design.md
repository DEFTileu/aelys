# AELYS Companion — прошивка ESP32-S3 (дизайн)

Статус: **PROPOSED** (по AGENTS.md решения в статусе PROPOSED требуют одобрения владельца).
Дата: 2026-11-12. Основа: отчёт `reports/Прошивка ESP32 для AELYS.md` и заметки в `research_notes/Прошивка ESP32 для AELYS/`.

Пометки: **[владелец]** — сказал владелец; **[моё решение]** — выбор автора дизайна, можно оспорить; **[открыто]** — нужно решение владельца.

## 1. Зачем

AELYS сейчас живёт в браузере, на Mac и на Android. Компаньон — физическое «окно» в AELYS на столе: всегда включён, показывает, что важно прямо сейчас, и даёт сделать пару действий одним касанием, не открывая приложение. Владелец хочет «свою ОС, связанную с AELYS» на подключённой плате ESP32-S3 **[владелец]**.

Под «ОС» здесь понимается собственная прошивка поверх ESP-IDF/FreeRTOS со своим интерфейсом и связью с AELYS, а не ядро с нуля **[моё решение]**: своё ядро не даёт ничего, кроме потери Wi-Fi/TLS/OTA из IDF.

Успех v1: плата сама подключается к AELYS, переживает перезагрузки и обрывы сети, показывает задачи/события/уведомления/фокус-таймер в течение секунд после изменения, и обновляется по воздуху без кабеля.

## 2. Цели, не-цели, анти-цели

**Цели v1** [моё решение]:
1. Привязка платы к аккаунту через существующее QR/SAS-сопряжение (ключ P-256 на плате).
2. Постоянный канал `wss://` к бэкенду с push-событиями.
3. Главный экран: часы, следующий дедлайн, следующее событие календаря, счётчик непрочитанных уведомлений, фокус-таймер.
4. Действия с платы: старт/пауза/стоп фокус-сессии, «отметить уведомление прочитанным», «задача выполнена».
5. OTA с откатом, метрики памяти и стабильности в бэкенд.
6. Работа офлайн: последний снимок данных и часы показываются без сети, с пометкой «нет связи».

**Не-цели v1** [моё решение] (возможны позже):
- голос, wake word, микрофон и динамик (фаза 5, только после замеров памяти);
- AI-чат на плате; LLM на устройстве;
- Telegram-отправка, почта, финансы на экране;
- магазин приложений / оболочка Brookesia «phone»;
- BLE-провижининг из Android-приложения (в v1 — Improv по USB).

**Анти-цели** (провал, даже если «работает»):
- плата с полным доступом владельца — украденная плата не должна читать почту/финансы и тем более действовать от имени владельца;
- ключи LLM-провайдеров (BYOK) или refresh-токены на плате;
- токен в URL, `ws://` в проде;
- необратимые операции без явного «да» владельца: прожиг eFuse (Secure Boot, Flash Encryption Release, anti-rollback), стирание заводской прошивки без бэкапа;
- действия ассистента на плате в обход Policy Engine;
- кирпич после OTA (обязателен откат).

## 3. Ограничения

- Плата (проверено `esptool flash-id` 2026-11-12): ESP32-S3 QFN56 rev v0.2, 240 МГц ×2, **8 МБ встроенной PSRAM (octal), 32 МБ флеша (quad)**, USB-Serial/JTAG (`/dev/cu.usbmodem1101`, MAC 7C:0C:5F:42:48:44). Совпадает с Waveshare ESP32-S3-Touch-AMOLED-1.75C: круглый AMOLED 466×466 (CO5300, QSPI, свой GRAM), тач CST9217, IMU QMI8658, питание AXP2101 + аккумулятор, кодек ES8311 + микрофоны ES7210, две боковые кнопки. Модель по шелкографии не сверена. Демо Waveshare копирует код в PSRAM (`Read only data copied and mapped to SPIRAM`), поэтому в его логе видно лишь ~4 МБ PSRAM.
- Владелец **[владелец]**: своя прошивка на C/C++, без чужой (Pip и пр. — только как источник идей), максимально быстрая и экономная по памяти, «чтобы вообще не лагало».
- Бэкенд — облачный FastAPI на Railway + Postgres; всё под `/api/v1`, типизированные коды ошибок, идемпотентные записи (AGENTS.md).
- AGENTS.md: без новых сервисов/брокеров без обоснования (поэтому не MQTT), идентичность и права устройства обязательны, автоматизация только через Policy Engine, UI-дизайн только по явной инструкции владельца.
- Внутренняя RAM — главный ресурс: Wi-Fi ~120 КБ, BLE ~120 КБ, TLS 22–42 КБ на соединение.

## 4. Как устроено

### 4.1 Стек [моё решение]
- **ESP-IDF v6.1**, **C11 для всего ядра** (UI, протокол, драйверы); C++17 допустим только как тонкая склейка, **без исключений и RTTI** (`-fno-exceptions -fno-rtti`) [моё решение: C предсказуем по памяти и совпадает с LVGL/IDF]. Сборка `idf.py`, версия IDF закреплена в CI (`espressif/esp-idf-ci-action@v1` с явной версией).
- **LVGL 9** со **своим портом дисплея** (не `esp_lvgl_port`): прямой контроль над буферами, TE-синхронизацией и DMA. Драйвер CO5300 — `esp_lcd` (QSPI), тач/IMU/PMU — тонкие свои драйверы поверх `i2c_master`.
- Не тянуть тяжёлое: без Arduino, без Brookesia, без cJSON (парсер `jsmn` — без аллокаций), без BLE-стека в v1.
- Компоненты из ESP Component Registry, `dependencies.lock` в git, `sdkconfig` — нет (только `sdkconfig.defaults*`).

### 4.2 Где живёт код [моё решение]
`firmware/companion/` в этом монорепо — ESP-IDF проект:
```
firmware/companion/
  main/                 склейка, app_main, state machine
  components/net/       Wi-Fi, SNTP, переподключение с backoff
  components/identity/  ключ P-256, NVS (шифрованный), device_id
  components/link/      wss-клиент, протокол, очередь исходящих
  components/board/     дисплей CO5300 + свой LVGL-порт, тач, IMU, PMU, кнопки
  components/ui/        экраны LVGL — переносимый C без зависимостей от IDF
  sim/                  сборка того же components/ui под хост (SDL) для быстрых проверок и скриншотов
  components/ota/       esp_https_ota + откат
  partitions.csv, sdkconfig.defaults, sdkconfig.defaults.<board>
  test/                 Unity-тесты; чистая логика (протокол, state machine) — на цели linux
```

### 4.3 Состояния устройства
`BOOT → (нет Wi-Fi) PROVISION → CONNECT_WIFI → (нет ключа/привязки) PAIR → AUTH → ONLINE ⇄ OFFLINE`.
- PROVISION + PAIR одним шагом через USB **[владелец]**: владелец, уже залогиненный в веб-клиенте AELYS, подключает плату по USB и открывает новую страницу «Подключить компаньон» (Web Serial + Improv Serial). Страница передаёт плате Wi-Fi и одноразовый секрет сопряжения. Плата генерирует P-256 и вызывает `POST /pairing/request` с этим секретом; страница (доверенное устройство) показывает SAS-код рядом с кодом на экране платы и подтверждает `/pairing/{id}/approve`; плата опрашивает `/pairing/{id}/finish`. Камера и QR-скан не нужны. BLE в v1 не включается — экономия ~120 КБ. Web Serial работает в десктопных Chrome/Edge и Android Chrome; Safari/iOS — нет. Страница — новый UI, её макет согласуется с владельцем (AGENTS.md).
- AUTH: при каждом подключении — challenge + подпись (`aelys-device-login-v1\n{device_id}\n{nonce}`) → короткий access-токен. **Refresh-токен плата не хранит** [моё решение]: одноразовый ротирующийся refresh теряется при обрыве питания между ответом и записью в NVS; ключ — стабильный секрет, теряться нечему.
- OFFLINE: экспоненциальный backoff с джиттером (1 с → 60 с), экран показывает кэш и «нет связи».

### 4.4 Изменения в бэкенде (требуют ADR в `docs/DECISIONS.md`) **[открыто: одобрение владельца]**
1. Платформа `companion` в `PLATFORM` (`backend/app/core/device_auth.py`).
2. **Права устройства (scope)**: у `companion` доступ только к разрешённому списку — чтение агенды/уведомлений/фокуса и три действия из §2. Уведомления **[владелец]**: заголовки — только у видов задач, календаря и фокуса; для Telegram, автоматизаций и прочих видов плата получает лишь счётчик, без заголовка и текста. Фильтрация на сервере (allow-list по `kind`), тело уведомления плате не отдаётся никогда; в офлайн-кэш попадает только то, что пришло. Всё остальное → 403 с типизированным кодом. Проверка на уровне `current_principal`/зависимости, fail-closed.
3. Вход по подписи без выдачи refresh для `companion` (или выдача, но плата её игнорирует — решает реализатор).
4. Канал `WS /api/v1/devices/channel` по образцу `/api/v1/agents/channel`: Bearer только в заголовке, JSON с полем `type`, `ready`/`heartbeat`/`heartbeat_ack`, закрытие 4401/4403 при проблемах с учёткой.
5. HTTP-маршрут агенды: `build_agenda` есть (`backend/app/domains/briefings.py`), маршрута нет — нужен снимок для экрана.
6. `GET /api/v1/devices/{id}/firmware` → `{version, url, sha256, size, min_version}`; образы подписаны.
7. Отзыв устройства уже есть (revoked device). При 4401/4403 или 401 плата **сначала заново входит по подписи**; привязку стирает и уходит в PAIR только если `/auth/device/challenge` отвечает, что устройство неизвестно или отозвано [моё решение по ревью: иначе плата сбрасывала бы привязку каждые 15 минут при истечении access-токена].
8. Источник push-изменений — таблица `sync_changes` (Railway: одна реплика, один процесс uvicorn, поэтому in-process рассылка допустима) [решение реализатора по ревью].

### 4.5 Протокол канала (JSON, текстовые кадры) [моё решение, детали — реализатору]
- Плата → сервер: `hello {fw_version, board, features}`, `heartbeat`, `metrics {heap_min_internal, largest_block, psram_free, wifi_reconnects, uptime}`, `action {id, kind, payload}` (идемпотентный `id`).
- Сервер → плата: `snapshot {agenda, notifications_unread, focus}` при подключении, `patch {...}` при изменениях, `action_result {id, ok, error_code}`, `ota_available {version}`.
- Резерв под будущее: `{"type":"mcp", ...}` по схеме xiaozhi (плата — MCP-сервер, вызовы только через Policy Engine) и бинарные Opus-кадры для голоса. В v1 не реализуются.
- Интервал heartbeat 30 с (гипотеза; проверить таймаут простоя прокси Railway).

### 4.6 Архитектура скорости и памяти [моё решение по отчёту; цифры — цели, проверяются замером на плате]

**Цели (бюджеты), проверяются в CI/на плате:**
| Метрика | Цель |
|---|---|
| анимации | 60 fps, синхронно с TE панели; худший кадр ≤ 25 мс |
| касание → изменение на экране | ≤ 50 мс |
| холодный старт → часы на экране | ≤ 1,5 с (без PSRAM memtest) |
| свободная внутренняя куча в ONLINE (минимум за сутки) | ≥ 80 КБ |
| внутренняя RAM под всё приложение (без Wi-Fi) | ≤ 100 КБ |
| размер образа | ≤ 2 МБ |

**Ядра и задачи:**
- Ядро 0: Wi-Fi/lwIP (встроенные задачи IDF), `net` (wss, разбор JSON, prio 5), `sense` (IMU по прерыванию FIFO, PMU раз в 1 с, prio 4).
- Ядро 1: `ui` (LVGL timer handler + рендер, prio 6) — единственная задача, трогающая LVGL; без мьютекса LVGL.
- Обмен: `net`/`sense` → `ui` через очередь коротких событий (≤ 64 Б) и двойной буфер состояния (`state_t` пишет `net`, `ui` забирает указатель атомарным swap). В рендер-пути нет блокировок, аллокаций и логов.

**Дисплей:**
- 466×466 RGB565 = 424 КБ на кадр — во внутреннюю RAM не влезает и не нужно: CO5300 держит кадр в своём GRAM.
- LVGL в режиме PARTIAL, **два буфера по 466×32 строк (~29 КБ каждый) во внутренней DMA-RAM**; пока DMA шлёт один, LVGL рисует в другой. Отправляются только грязные области; flush ждёт TE, чтобы не было разрывов.
- QSPI 80 МГц; байтовый порядок RGB565 готовится сразу в «панельном» виде (без перестановки байтов при отправке).
- Шрифты и иконки — пре-рендер в A8/битмапы на этапе сборки; на лету не масштабировать, не использовать opacity-слои, крупные трансформации и тени. Тёмный UI: на AMOLED чёрный пиксель не светится — экономия батареи.

**Память:**
- Внутренняя RAM — только: DMA-буферы дисплея, стеки задач, TLS (динамические буферы, ~22 КБ на сессию), ISR/горячие структуры.
- PSRAM (8 МБ): куча LVGL (свой `lv_mem` поверх `heap_caps_malloc(MALLOC_CAP_SPIRAM)`), JSON-буферы, кэш снапшота, ассеты, загруженные из LittleFS. `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048`.
- mbedTLS: `CONFIG_MBEDTLS_DYNAMIC_BUFFER` + `DYNAMIC_FREE_CONFIG_DATA` + `DYNAMIC_FREE_CA_CERT`, cert bundle только нужных CA.
- Wi-Fi/lwIP: профиль буферов ниже Default; `SPIRAM_TRY_ALLOCATE_WIFI_LWIP`.
- Статические пулы вместо malloc в цикле работы; после старта число аллокаций во внутренней куче не растёт (проверка в метриках).

**CPU:**
- `-O2` (Performance), I-cache 32 КБ / D-cache 64 КБ, line 64 Б; горячие циклы рендера — `IRAM_ATTR`.
- На S3 нет аппаратного деления/корня во float — в попиксельном коде только целочисленная арифметика/таблицы.
- Логи в релизе — уровень WARN, компилируются вне горячих путей.

**Питание (плата с аккумулятором):**
- Экран: тускнеет через N с, гаснет позже; экраном вниз 1 с — гаснет сразу; будит касание, кнопка, подъём (IMU).
- `esp_pm` DFS 80–240 МГц + auto light sleep; Wi-Fi `WIFI_PS_MAX_MODEM` с DTIM 3 при выключенном экране, `MIN_MODEM` при включённом.
- PM-лок `NO_LIGHT_SLEEP` держит только `ui` во время анимации.

**Надёжность:** `CONFIG_ESP_TASK_WDT_PANIC`, coredump во флеш, выгрузка дампа в бэкенд при следующем подключении; метрики раз в 5 мин: минимум внутренней кучи, крупнейший блок, fps/худший кадр, high-water стеков, переподключения.

### 4.7 Разделы флеша (32 МБ)
`nvs` 24 КБ, `otadata` 8 КБ, `phy_init` 4 КБ, `ota_0`/`ota_1` по 4 МБ, `coredump` 64 КБ, `storage` (LittleFS) — остаток (~23 МБ) под шрифты, иконки, кэш снапшота.

### 4.8 Безопасность
- Уровень 1 (v1): шифрование NVS по HMAC-ключу в eFuse — **прожиг одного eFuse-блока необратим, делается только после явного «да» владельца** [открыто]. До этого — NVS без шифрования, с пометкой в доке.
- Подпись OTA-образов `CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT` (без eFuse). Ключ подписи хранится **только на Mac владельца**, вне репозитория и CI **[владелец]**; релиз — ручной скрипт: сборка → подпись → загрузка через owner-only маршрут бэкенда. CI только собирает и тестирует, не подписывает.
- Secure Boot / Flash Encryption Release / anti-rollback — не в v1.
- Перед любыми eFuse-операциями — прогон в QEMU.

### 4.9 Порядок работ (фазы)
Разрешения на работу с платой **[владелец]**: одно «да» покрывает перезагрузку, бэкап и обычные перепрошивки приложения/OTA-разделов. Отдельное «да» каждый раз нужно для: любых операций с eFuse, удаления бэкапа, `erase-flash` целиком.

0. **Опознание и бэкап платы**: `flash-id` — сделано (см. §3). Осталось: `get-security-info`, `read-flash 0 ALL backup_7C0C5F424844.bin` (хранить вне git, может содержать Wi-Fi-пароли).
1. **Скелет прошивки**: IDF-проект, свой порт дисплея + тач, sim-сборка UI на хосте, экран «часы + статус», метрики fps/кучи в лог — и **замер бюджетов §4.6 до любых фич**. Затем Improv-провижининг, Wi-Fi, SNTP. Затирает демо Waveshare; бэкап из фазы 0 позволяет вернуть.
2. **Бэкенд**: ADR, платформа `companion`, scope, вход по подписи, канал `/devices/channel`, маршрут агенды. Тесты на scope (fail-closed).
3. **Сопряжение и главный экран**: PAIR с QR/SAS, AUTH, snapshot/patch, офлайн-кэш, действия.
4. **OTA и надёжность**: firmware-endpoint, `esp_https_ota`, откат по успешному `hello`, coredump, CI-сборка.
5. *(опционально)* **Голос**: только если после фаз 1–4 минимум внутренней кучи ≥ 120 КБ; отдельный дизайн.

### 4.10 Инструменты для разработки [моё решение; установка — с согласия владельца]
- Espressif docs MCP (`claude mcp add --transport http espressif-documentation https://mcp.espressif.com/docs`) и Component Registry MCP.
- Скиллы `pedrominatel/awesome-esp-ai` (`esp-idf`, `esp-idf-components`, `esp-idf-v6-migration`) — прочитать SKILL.md до установки; у репо нет лицензии.

### 4.11 Пропажа, экстренная карточка, Wi-Fi с телефона **[владелец, 2026-11-12]**
Управляется из приложения AELYS: Settings → Devices → Aelys (макеты — страница «ACTUAL AELYS Companion App» в дизайн-проекте).
- **Режим пропажи**: включается из приложения командой по каналу. Плата показывает только выбранные владельцем контакты, сообщение и QR; всё остальное скрыто, с платы режим не выключается. Данные режима пишутся в NVS, поэтому экран работает и без сети и после перезагрузки. Выключение в приложении — с повторной аутентификацией.
- **Найти Элис**: команда `play_sound` — звук + вспышка кольца.
- **Экстренная карточка (ICE)**: удержание обеих кнопок 2 с с любого экрана, включая сон и пропажу. Поля выбирает владелец; хранятся локально в NVS.
- **SOS** — *предложение, не v1*: из карточки, удержание верхней 3 с → 5 с отсчёт с отменой → бэкенд отправляет тревогу экстренным контактам (Telegram/push) с временем и последней Wi-Fi сетью. Отправка идёт через Policy Engine; нужен отдельный ADR и тест ложных срабатываний.
- **Wi-Fi с телефона**: если плата онлайн — приложение шифрует SSID+пароль публичным ключом P-256 платы (ECIES), бэкенд передаёт непрозрачный блоб, расшифровывает только плата; сервер пароль не видит. Плата хранит до 5 сетей в NVS, умеет отчитаться списком видимых сетей (scan). Если плата офлайн/первая настройка — только USB-страница (BLE в v1 нет; BLE-провижининг можно добавить позже, включая его лишь на время настройки).
- Бэкенд: новые типы сообщений канала (`lost_mode`, `play_sound`, `wifi_add`, `wifi_scan`, `ice_update`) и права `companion` на их приём; запись этих команд — только с устройств владельца, не с самой платы.
- Приватность: контакты в режиме пропажи и ICE видны любому, кто держит плату, — владелец выбирает поля явно.
- **Контакты владельца по умолчанию [владелец, 2026-11-12]**: телефон и Telegram владельца вшиваются в прошивку как заводские значения для режима пропажи и ICE (QR ведёт в Telegram). Они лежат в `firmware/companion/main/owner_contact.local.h` (`OWNER_PHONE`, `OWNER_TELEGRAM`, `OWNER_QR_URL`), который в `.gitignore`: репозиторий публичный, номер в git не попадает. Сборка без этого файла падает с понятной ошибкой; в git лежит только `owner_contact.example.h`. Значения из приложения (`lost_mode`, `ice_update`) пишутся в NVS и перекрывают заводские.
