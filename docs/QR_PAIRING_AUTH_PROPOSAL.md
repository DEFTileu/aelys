# Passwordless device authentication and QR pairing

2026-10-31 · owner direction: first-run ownership and device linking should need no
login/password; a phone is linked by scanning a QR code; web and desktop are linked
the same way; security stays as high as practical. The owner approved this design
("начинай реализацию"). Decision record: ADR-025. Status: **backend slice
implemented (phases 1-2); clients, native key storage and the password switch-off
are not**.

## Decisions taken (defaults proposed to and accepted by the owner)

1. Passwords stay as an optional fallback for existing owners. Creating an owner with a
   password is **off by default** (`AELYS_PASSWORD_BOOTSTRAP_ENABLED=false`, owner
   instruction 2026-10-31); ownership is claimed only with a setup token. Password
   sign-in for an existing owner stays on (`AELYS_PASSWORD_LOGIN_ENABLED`) because no
   client can pair yet; switching it off is a later, explicit step (needs one key-bound
   device and the recovery path).
2. A browser is a lower-trust device class (non-extractable WebCrypto key; XSS can
   still use it). Planned: shorter sessions, QR re-pairing, no secrets export, no agent
   execution. Not enforced yet.
3. Recovery uses a server-side command (`python -m app.core.admin setup-token
   --recovery`); shell access to the server is the trust anchor. A printed recovery key
   is planned as a second path.
4. Pairing over a plain LAN without internet is not designed yet; it needs certificate
   pinning for a self-signed server and is deferred.

## Protocol (implemented in `backend/app/core/device_auth.py`)

Keys: each device holds an ECDSA P-256 key. The server stores only the public key
(uncompressed point, base64url; SPKI DER is accepted and normalized). Signatures may
be raw `r||s` (WebCrypto) or DER (Secure Enclave, Android Keystore).

**First owner.** On an empty server the console prints a one-time setup token
(`secrets.token_urlsafe(24)`, 30 minutes, only its SHA-256 stored). The first device
posts the token with its public key to `POST /auth/setup/claim`, which creates the
owner without email or password, registers the device and returns a session. A
`recovery` token (issued by the admin command) enrolls a device for the existing owner.

**Device login.** `POST /auth/device/challenge` returns a 60 s single-use nonce;
`POST /auth/device/login` takes a signature over
`aelys-device-login-v1\n{device_id}\n{nonce}`. The challenge is burned before the
signature is checked. Sessions are the existing session-bound tokens with a device id,
so `/auth/refresh` rotation, revocation and `current_principal` checks are unchanged.

**Migration.** `POST /devices/register-key` lets a password session register a key; the
key must sign `aelys-device-register-v1\n{owner_id}\n{public_key}` (proof of possession).

**QR pairing.** Secrets are generated by clients; the server stores only the SHA-256
and never the raw secret. Two directions share one state machine
(`pending -> claimed -> approved -> consumed`, plus `rejected`/`locked`):

- `invite`: a key-bound trusted device calls `POST /pairing/invite`, shows
  `pairing_id` + secret in a QR; the new device calls `.../claim` with the secret and its key.
- `request`: a new device (web or desktop without a camera) calls `POST /pairing/request`
  with its key and shows the QR; a trusted phone scans it.

The new device shows a six-digit code derived locally from the secret, the pairing id
and its public key (HMAC-SHA256). The owner **types that code into the trusted device**;
`.../approve` recomputes it server-side. A substituted key gives a different code, so a
relayed or photographed QR cannot be approved by accident. After approval the new device
signs `aelys-pairing-finish-v1\n{pairing_id}` at `.../finish` (proof of possession) and
receives its first session exactly once. Only key-bound devices (not password sessions)
may invite, inspect, approve or reject.

## Threat model summary

| Threat | Control |
| --- | --- |
| First-visitor takeover of a public server | Setup token from the console; password bootstrap can be disabled |
| QR photographed or relayed | 120 s TTL, single claim, typed confirmation code, key fingerprint on inspect |
| Secret guessing | 256-bit secrets, constant-time compare, lock after 5 failures, caps on pending pairings |
| Stolen database | Public keys and hashes only; no password hashes for key-bound owners |
| Replay of a login signature | Single-use 60 s challenges, burned before verification |
| Pairing completed by someone without the key | Finish requires a signature from the claimed key |
| Lost device | Existing per-device revoke; audit entries for enrollment, approve and reject |

## Not done yet

- Native key storage (Secure Enclave, Android Keystore), camera scanning and QR display UI,
  and the native-app setup-token screens.

## Web client (implemented 2026-10-31)

The web app registers itself with a setup token: a non-extractable WebCrypto P-256 key is
generated in the browser and kept in IndexedDB bound to the server origin; the server returns
a session, and no refresh credential is stored. Later sessions are renewed by signing a server
challenge, so there is no password or stored secret in `localStorage`/`sessionStorage` beyond the
short-lived access token. After an explicit sign-out the login screen offers "sign in with this
device". An unknown or revoked device deletes its local key. `GET /auth/browser/status` and
`/auth/native/status` report `password_setup` so clients show password creation only while the
server allows it. Browser-held keys remain a lower-trust class; QR scanning is not wired in the UI.
- Server certificate pinning carried in the QR; the client must compose the QR with the
  server URL and pin.
- Refresh-token reuse detection that revokes the device, device trust tiers, a recovery key,
  and an explicit switch to disable password login for an existing owner.
- A shared rate-limit store for multi-instance deployments (limits are per process today;
  `AELYS_TRUSTED_PROXY_COUNT` must be set behind a reverse proxy) and an external security
  review before this is called production-grade.
