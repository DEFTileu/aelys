# Aelys backend/runtime security review addendum

Status: review findings only. This addendum does not claim the backend or runtime is complete or release-ready.

Follow-up status after lead integration: the hardcoded attestation example was
replaced with a real sandbox probe and challenge round-trip; signed request
bytes are now structurally matched to the verified request; metadata rows are
owner/device checked; WebSocket bearer tokens use the Authorization header;
non-loopback runtime channels require `wss://`; run claims use row locking and
lease IDs; lifecycle events, cancellation, and durable idempotency are checked;
Keychain references are derived internally from the provider; and Codex/Claude
credential directories are denied by the sandbox profile. The remaining
release blockers are genuine vendor credentialed CLI compatibility and
independently trusted probe/helper provenance on supported macOS versions.

Scope: `backend/` and `apps/runtime/` against `docs/SECURITY.md`, `docs/AGENT_RUNTIME.md`, `docs/AI_HARNESS.md`, and `docs/ACCEPTANCE_TESTS.md`. The existing `SECURITY_ARCH_REVIEW.md` was preserved; this file records gaps found while independently validating its claims.

## Prioritized findings

### F-01 — Critical / release blocker: isolation attestation is self-asserted

The backend treats a device signature over boolean evidence as sufficient to set `ProjectGrant.isolation_validated`. It verifies the device public key, signature, device ID, expiry, grant ID, project ID, grant nonce, and boolean values, but it does not verify that the evidence came from the runtime's sandbox probe or bind it to a profile, executable digest, OS result, or a one-time challenge. See [`backend/app/agents/api.py:19`](backend/app/agents/api.py:19) and [`backend/app/agents/api.py:81`](backend/app/agents/api.py:81).

The runtime path has the same trust problem: `validate_project_with_network` accepts a caller-supplied `probe_program`, parses its self-reported JSON, and sets `os_level_enforced: true` without independently establishing enforcement ([`apps/runtime/src/isolation.rs:105`](apps/runtime/src/isolation.rs:105), [`apps/runtime/src/isolation.rs:122`](apps/runtime/src/isolation.rs:122)). The shipped attestation example does not run a probe at all; it constructs `ProbeResult` with every field set to `true` ([`apps/runtime/examples/attest.rs:22`](apps/runtime/examples/attest.rs:22)).

Impact: a process that can use the enrolled device key can enable a project grant by signing claims without demonstrating outside-path, credential, symlink, subprocess, or network isolation. This directly defeats the prerequisite for autonomous execution in `docs/SECURITY.md:41-49`, `docs/AGENT_RUNTIME.md:70-77`, and acceptance criterion F-4.

Required remediation: make the attestation verifier consume a server challenge and accept evidence only from a fixed, integrity-checked probe/profile path whose result is generated by the runtime after the probes execute. Bind the report to the canonical project root/profile and runtime build, reject stale/future timestamps, consume the challenge exactly once, and keep the grant disabled on any unverifiable result. Do not ship an attestation helper that signs hardcoded evidence.

### F-02 — High / release blocker: cancellation, revocation, and run events are not enforced end to end

The HTTP cancel handler directly sets the database status to `cancelled` and returns; it sends no cancellation command to the Mac runtime and carries no lease identifier ([`backend/app/agents/api.py:131`](backend/app/agents/api.py:131)). The runtime channel exposes claim and heartbeat requests but no cancel request ([`apps/runtime/src/channel.rs:114`](apps/runtime/src/channel.rs:114)). A running process can therefore continue after the API reports cancellation, and a later runtime event can overwrite that state because `run_event` accepts any listed state without a transition or lease check ([`backend/app/agents/api.py:65`](backend/app/agents/api.py:65)).

The WebSocket also checks `device.revoked_at` only before accepting the connection. The receive loop does not recheck the device, grant, or run authorization, so an already-open socket can continue to heartbeat, upload metadata, attest, and update runs after device revocation ([`backend/app/agents/api.py:41`](backend/app/agents/api.py:41), [`backend/app/agents/api.py:47`](backend/app/agents/api.py:47)).

Impact: acceptance criteria F-6 and security gates 4 and 5 are not met; cancellation can leave an orphan or still-authorized CLI, and revocation is not immediate for an active channel.

Required remediation: make cancel a durable, lease-bound runtime command; require the current lease ID on claim, heartbeat, event, and cancel acknowledgements; enforce the documented state machine atomically; reject terminal-state rewrites; and revalidate device/grant authorization for every message or close the socket on revocation.

### F-03 — High: backend claims are race-prone and not lease-bound

`run_claim` performs a read, checks `status == "queued"`, assigns `starting`, and commits without a row lock or conditional update ([`backend/app/agents/api.py:71`](backend/app/agents/api.py:80)). Two authenticated channel consumers can observe the same queued row and both receive a claim acknowledgement. The `AgentRun` model stores only `lease_until`, not a lease ID ([`backend/app/core/models.py:176`](backend/app/core/models.py:178)), while runtime messages identify a run only by `run_id` ([`apps/runtime/src/channel.rs:122`](apps/runtime/src/channel.rs:127)).

Impact: replay or concurrent delivery can start duplicate local processes, and stale events from an earlier claimant cannot be distinguished from the current claimant. This violates the lifecycle requirements in `docs/AGENT_RUNTIME.md:108-113` and acceptance criterion F-2.

Required remediation: use an atomic `UPDATE ... WHERE status='queued'` or `SELECT FOR UPDATE`, persist a random lease ID and owner, require it on every runtime lifecycle message, and expire/reconcile the lease before allowing a new claim.

### F-04 — High: runtime credential lookup is not policy-scoped

`MacOsKeychainReader` accepts any non-empty service and account and invokes `security find-generic-password` with those caller-provided values ([`apps/runtime/src/credentials.rs:26`](apps/runtime/src/credentials.rs:51)). `execute_once_with_credential` passes the service and account through without checking them against a provider/device/project policy ([`apps/runtime/src/runner.rs:104`](apps/runtime/src/runner.rs:129)).

Impact: any caller that reaches this coordinator API can request an arbitrary accessible generic Keychain item and inject its plaintext into the CLI environment. The current backend path does not yet wire this method to remote runs, and vendor execution is conservatively disabled by default, so this is a pre-enable isolation blocker rather than evidence of an already reachable remote exploit.

Required remediation: resolve credentials from an internal policy-bound reference, allow only fixed service/account namespaces for the selected provider, keep the mapping out of run/task input, and audit only the reference and policy decision.

### F-05 — High: authenticated runtime channel permits bearer-token URL leakage and plaintext endpoints

The backend accepts `access_token` in the WebSocket query string as a fallback to the Authorization header ([`backend/app/agents/api.py:31`](backend/app/agents/api.py:34)); the existing API contract test uses that form ([`backend/tests/test_api_contracts.py:34`](backend/tests/test_api_contracts.py:36)). Query strings are commonly retained by proxy/access logs, browser history, and tracing systems. The runtime client accepts the endpoint verbatim and uses `connect_async` without enforcing `wss://` ([`apps/runtime/src/channel.rs:189`](apps/runtime/src/channel.rs:207)); the runtime README documents `ws://` as the example endpoint ([`apps/runtime/README.md:31`](apps/runtime/README.md:37).

Impact: a device access token can be exposed through ordinary URL logging, and a deployment can accidentally run the authenticated channel without transport encryption, contrary to `docs/SECURITY.md:20-27` and `docs/AGENT_RUNTIME.md:16`.

Required remediation: remove query-token authentication from the production route, reject non-TLS remote endpoints except an explicit loopback development mode, and add tests that verify the endpoint scheme and token never enters URL/log fields.

### F-06 — Medium: cloud metadata validation is an allowlist of keys only and permits cross-owner overwrite

The channel checks only whether metadata field names are in `METADATA_FIELDS`; values are not type- or size-validated, `project_id` is not checked against an owner project or device grant, and `None` is accepted for `device_id` ([`backend/app/agents/api.py:51`](backend/app/agents/api.py:56)). More seriously, an existing `AgentSessionIndex` is loaded by global primary key and overwritten without checking its current owner/device ([`backend/app/agents/api.py:59`](backend/app/agents/api.py:63)).

Impact: a device that knows another session index ID can overwrite that cloud metadata row, and untrusted content can be placed in nominally safe fields such as `state` or `adapter`. This weakens the cloud metadata boundary required by `docs/AGENT_RUNTIME.md:30-35` and acceptance criteria E-5.

Required remediation: validate a typed bounded projection, require the authenticated device ID, verify project ownership and grant scope, and update rows using an owner/device predicate or an owner-scoped composite key.

## Current audit follow-up — 2026-10-28

This section supersedes no earlier finding and records additional gaps found by
auditing the current working tree. It is evidence for follow-up only; the
repository must not be treated as complete or release-ready.

### F-07 — Critical / release blocker: attestation still lacks provenance and signed-request integrity

The backend verifies the device signature over `envelope["signed_payload"]`,
but does not require that value to equal the canonical serialization of the
current `request`. The authorization checks then read the mutable `request`
object. A valid signed envelope can therefore be replayed with its request
claims edited without invalidating the checked signature. The verifier also
checks only expiry, not a bounded issued-at window or a replayed request nonce
([`backend/app/agents/api.py:28-39`](backend/app/agents/api.py:28)).

The runtime accepts a caller-supplied `probe_program` and treats a successful
JSON result plus a challenge echo as sufficient; `os_level_enforced` is set to
`true` in code rather than established from an independently verified probe or
OS result ([`apps/runtime/src/isolation.rs:106-139`](apps/runtime/src/isolation.rs:106)).
The probe executable can also be overridden through `AELYS_PROBE_PATH`
([`apps/runtime/examples/attest.rs:32-45`](apps/runtime/examples/attest.rs:32)).
The backend checks booleans, grant/device/project/nonce fields, and the device
signature, but never binds the evidence to a fixed probe digest, profile
digest, canonical project root, runtime build, or OS enforcement result
([`backend/app/agents/api.py:115-123`](backend/app/agents/api.py:115)).

The grant nonce is one-time state, so freshness improved, but it is not
attestation provenance. Autonomous execution must remain disabled until the
probe/profile path is fixed and integrity-checked, the signed request is
canonicalized, and the evidence is independently bound to the validated
runtime and profile.

### F-08 — High / release blocker: cancellation, grant revocation, and lease expiry are not end-to-end

The HTTP cancel endpoint only sets `cancellation_requested` for an active run;
it does not carry a lease ID or issue a command to the connected runtime
([`backend/app/agents/api.py:165-172`](backend/app/agents/api.py:165)). The
runtime's `cancel_run` is a client-to-backend request, while the local process
supervisor polls only its own in-memory `RunManager` flag
([`apps/runtime/src/channel.rs:124-126`](apps/runtime/src/channel.rs:124),
[`apps/runtime/src/runner.rs:127-153`](apps/runtime/src/runner.rs:127)). No
current integration connects the HTTP cancellation flag to that supervisor or
proves that an already running vendor process is killed.

Lease checks protect backend channel messages, but the local execution path
does not check lease expiry before starting, while waiting, or before marking a
process terminal ([`apps/runtime/src/runner.rs:70-153`](apps/runtime/src/runner.rs:70)).
The backend returns `LEASE_UNAVAILABLE` for an expired `starting` or `running`
row without reconciling it to an expired/reclaimable state
([`backend/app/agents/api.py:105-114`](backend/app/agents/api.py:105)).
Concurrent HTTP run creation is also a read-then-insert idempotency check with
no database uniqueness constraint or transaction claim
([`backend/app/agents/api.py:148-151`](backend/app/agents/api.py:148),
[`backend/app/core/models.py:176-179`](backend/app/core/models.py:176)).

Device revocation is rechecked when the established socket receives a message
([`backend/app/agents/api.py:57-61`](backend/app/agents/api.py:57)), and the
existing test proves a subsequent heartbeat is rejected
([`backend/tests/test_api_contracts.py:59-70`](backend/tests/test_api_contracts.py:59)).
That does not close an idle socket proactively, revalidate token expiry, or
apply project-grant revocation to `run_event`; the latter checks device/run/lease
only ([`backend/app/agents/api.py:85-96`](backend/app/agents/api.py:85)).

### F-09 — High / pre-enable blocker: credential lookup is namespace-limited but not policy-scoped

`CredentialRequest` exposes service and account strings to its caller, and the
runner passes them directly to the credential loader without a device, project,
grant, or policy reference ([`apps/runtime/src/runner.rs:23-27`](apps/runtime/src/runner.rs:95-123)).
The production Keychain reader restricts real lookups to two Aelys services and
the `default` account, but `load_cli_credential` retains a compiled
`test-only-*` service bypass and allows an arbitrary account on that path
([`apps/runtime/src/credentials.rs:64-83`](apps/runtime/src/credentials.rs:64)).
This is test scaffolding in a production library boundary, not a policy-bound
credential reference.

The Seatbelt profile denies several named credential locations but does not
deny `$HOME/.codex`; the documented Codex login location is
`~/.codex/auth.json`, and `env_clear()` does not prevent direct filesystem
access ([`apps/runtime/src/sandbox.rs:52-56`](apps/runtime/src/sandbox.rs:52),
[`apps/runtime/README.md:66-69`](apps/runtime/README.md:66)). A credentialed
vendor run therefore remains blocked until credential resolution is internal,
device/project scoped, and the profile denies the complete approved credential
surface.

### F-10 — High / release blocker: the mounted sync API does not implement the documented commit-order protocol

`app.main` mounts `backend/app/sync/api.py`, not the typed service/router path
([`backend/app/main.py:30-35`](backend/app/main.py:30)). The mounted push route
flushes an autoincrement `SyncChange.seq` and uses it as the returned cursor
before the transaction commits ([`backend/app/sync/api.py:37-66`](backend/app/sync/api.py:37)).
Two PostgreSQL transactions on different resources can allocate sequence N,
then N+1 commits first; a client that advances past N+1 can miss N when it later
commits. This is the exact allocation-order failure explicitly excluded by
[`docs/SYNC_PROTOCOL.md:46-50`](docs/SYNC_PROTOCOL.md:46).

The mounted bootstrap endpoint reads a watermark and the records in separate
statements without a stable snapshot or page token
([`backend/app/sync/api.py:76-82`](backend/app/sync/api.py:76)). The live path
also lacks the typed compaction/reset and tombstone handling represented by
the separate sync service. The existing sync-engine tests exercise the fake
store protocol, not this mounted PostgreSQL path.

There are two additional ownership defects in the mounted path: an owner-only
access token can submit an arbitrary body `device_id` because the check runs
only when `current_principal` returned a device, and an existing
`ClientOperation` is returned by global primary key without checking its owner
or device ([`backend/app/sync/api.py:33-43`](backend/app/sync/api.py:33)).

### F-11 — High: transcript privacy is enforced by a bypassable denylist on the live sync path

The mounted `Operation` validator rejects only a few substrings in serialized
JSON ([`backend/app/sync/api.py:21-28`](backend/app/sync/api.py:21)). It accepts
neutral-key payloads such as `{"messages": ["private content"]}`,
`{"content": "CLI output without keyword"}`, and
`{"local_session_ref": "/Users/me/.codex/auth.json"}`. The stricter
allowlist and transcript-key validation in `backend/app/sync/validation.py`
is not used by the mounted endpoint. This leaves raw private content and local
paths dependent on client naming conventions rather than resource schemas.

The runtime channel has the same shape problem for metadata: it allowlists keys
but does not type, bound, or grant-scope values before persisting `adapter`,
`state`, `message_count`, timestamps, and the session identifier
([`backend/app/agents/api.py:64-84`](backend/app/agents/api.py:64)). The
Rust cloud projection itself contains only neutral fields, which is a passing
local contract, but it does not compensate for the untyped backend ingress.

### F-12 — High: refresh tokens are accepted as ordinary API bearer tokens

`current_principal` decodes the bearer token and resolves its owner but never
requires `claims["typ"] == "access"`
([`backend/app/core/security.py:57-68`](backend/app/core/security.py:57)).
`decode_token` accepts both token kinds, and refresh tokens live for the longer
refresh period ([`backend/app/core/security.py:27-34`](backend/app/core/security.py:27),
[`backend/app/core/api.py:20-24`](backend/app/core/api.py:20)). A refresh token
can therefore call regular API routes directly and bypass the intended short
access-token lifetime. The existing tests cover refresh rotation, but not
refresh-token use against a protected endpoint.

### F-13 — High: AI streaming cancellation can be overwritten by completion

The AI cancel route immediately writes `status="cancelled"`, but it does not
signal the active stream or persist a cancellation handle
([`backend/app/ai/api.py:137-141`](backend/app/ai/api.py:137)). The stream
handler then runs to completion and unconditionally writes `status="completed"`
after `service.stream_sse` returns ([`backend/app/ai/api.py:123-135`](backend/app/ai/api.py:123)).
The execution service has an optional cancellation event, but the FastAPI path
never supplies one. Acceptance criterion D-8 is therefore unverified and the
final state is not stable under cancellation.

### F-14 — Medium / deployment blocker: default signing and encryption key is fail-open

The settings object uses `development-only-change-me` when
`AELYS_SECRET_KEY` is absent and has no startup validation
([`backend/app/core/config.py:4-9`](backend/app/core/config.py:4)). The same
key protects JWT signatures and the AES-GCM provider-secret envelope
([`backend/app/core/security.py:27-34`](backend/app/core/security.py:27),
[`backend/app/ai/crypto.py:6-11`](backend/app/ai/crypto.py:6)). The README asks
operators to set a random key, but the application does not fail closed when
they do not. A deployed default instance would make bearer forgery and provider
secret decryption practical.

### F-15 — Medium: CI and OpenAPI checks do not cover the stated completion gate

The current workflow runs Python compilation, pytest, Alembic against its
default local database, generated-spec diff, and Rust format/test/clippy
([`.github/workflows/ci.yml:12-26`](.github/workflows/ci.yml:12)). It has no
Python type check, Python lint, dependency/security scan, real PostgreSQL
integration job, or dedicated attestation/sync/cancellation security suite.
The generated document does match the working app at 63 paths, which is a
useful consistency check, but the live agent and sync handlers return empty
response schemas in OpenAPI and the WebSocket protocol is absent from the
OpenAPI document. Generation equality is not typed protocol validation.

## Gate disposition

### Latest lead follow-up

- F-07 signed-request integrity is fixed: the backend parses the signed bytes,
  requires structural equality with the received request, checks the bounded
  issued/expiry window, and the live attestation path passes. Probe provenance
  and helper/runtime integrity remain open.
- F-08 lease expiry, durable run idempotency, grant checks on run events, local
  lease expiry, process-tree cleanup, and reconnect tests are now covered.
  HTTP cancellation still reaches a live process through the runtime heartbeat
  polling contract; a persistent helper supervisor must provide the final
  process handle integration.
- F-09 caller-selected credential references and the test-only production
  bypass are removed. Provider service/account mapping is internal, and the
  sandbox denies `.codex` and `.claude` credential directories.
- F-10 mounted sync now uses the strict recursive validator, owner-wide
  PostgreSQL transaction serialization, and repeatable-read bootstrap. A full
  production compaction/reset protocol and PostgreSQL CI job remain open.
- F-11 metadata ingress now uses bounded typed Pydantic fields, exact device
  binding, project ownership, and an explicit allowlist.
- F-12 refresh tokens are rejected on ordinary bearer-protected routes. F-13
  AI stream completion no longer overwrites a cancelled run after a refresh.
- F-14 startup configuration now requires an explicit secret key; CI and tests
  provide non-production keys through their environment.
- The runtime probe slice now rejects arbitrary executables, resolves the
  bundled probe across binary/deps/examples layouts, hashes the runtime and
  probe before and after execution, binds evidence to the canonical profile,
  and serializes the three local digests into the signed attestation. The
  backend requires those bounded digest fields. This still does not replace
  signed release/code-signing verification or an installed helper lifecycle.

- The local checks currently pass: 36 Python tests with one deprecation warning,
  Python compilation, OpenAPI equality at 63 paths, 24 Rust unit tests, 13 Rust
  integration tests, formatting, and clippy.
- The passing runtime tests are conservative or local. They do not establish
  independent attestation provenance, real vendor CLI execution, durable
  helper restart reconciliation, orphan cleanup after restart, backend HTTP
  cancellation to a live process, or PostgreSQL commit-order behavior.
- Session discovery/search and vendor adapters remain compatibility probes or
  offline stubs; the backend search endpoint returns `MAC_OFFLINE` metadata
  only ([`backend/app/agents/api.py:136-140`](backend/app/agents/api.py:136)).
- The repository still has no frontend, Android wrapper, or installed helper
  lifecycle evidence, so the corresponding A, C, E, F, and H acceptance
  scenarios remain unchecked. These findings are sufficient to keep the
  completion gate closed.

## Fresh read-only completion/security audit — 2026-10-28

This audit rechecked the current working tree against `docs/SECURITY.md`,

### A-01 — Critical / release blocker: attestation provenance is still not independently trusted

The signed request is now bound to the received request object and the grant
nonce is consumed, which closes the earlier unsigned-request mutation issue.
The remaining attestation result is still a set of device-signed booleans:
`backend/app/agents/api.py:139-147` does not bind it to a fixed probe digest,
Seatbelt profile digest, canonical project root, runtime build, or an
independently established OS enforcement result. The runtime sets
`os_level_enforced: true` in `apps/runtime/src/isolation.rs:131-139` after
accepting a caller-supplied probe path, and the example permits
`AELYS_PROBE_PATH` at `apps/runtime/examples/attest.rs:32-42`.

The default runtime gate remains unavailable, so this is currently a fail-safe
pre-enable weakness rather than evidence that the remote route is already
usable. It still blocks F-4 and the autonomous execution security gates until
the evidence is provenance-bound and verified on the supported macOS target.

### A-02 — High / pre-enable blocker: vendor credentialed execution remains unavailable, and its local seam is not policy-bound

`VendorAdapter::probe_support` always reports `can_run: false` at
`apps/runtime/src/adapter.rs:83-94`; the installed CLI compatibility test only
runs `--version` and `--help` with isolated configuration and explicitly
asserts `can_run == false` (`apps/runtime/tests/runtime_contracts.rs:413-465`).
The current host has `codex-cli 0.163.0` and Claude Code `2.1.311`, but no
credentialed run, native session compatibility, or supported authenticated
invocation has been proven.

There is a separate execution seam in
`apps/runtime/src/runner.rs:93-117` that can inject a fixed-provider Keychain
value into a process when a caller supplies an adapter reporting
`can_run == true` and a validated test gate. The production lookup is
namespace-limited in `credentials.rs`, and `.codex`/`.claude` are denied by
the Seatbelt profile, but the credential request still has no device,
project, grant, or policy identity. The backend does not wire this method to a
persistent helper or remote run. Therefore the vendor credential gate remains
closed, and enabling it would require a device-bound broker plus an actual
credentialed compatibility run.

### A-03 — High / release blocker: AI cancellation is stable against DB overwrite but not end-to-end

The current FastAPI stream checks for a cancelled row after provider streaming
and therefore no longer overwrites the database status with `completed`
(`backend/app/ai/api.py:129-143`). However, the cancel endpoint only writes
the database flag at `backend/app/ai/api.py:146-152`; it does not retain or
signal an active cancellation event, close the provider stream, or prevent
provider work and SSE chunks already in flight. The optional cancellation
event in `AIExecutionService.stream_sse` is never passed by this route.
The cancellation test that passes is for the separate in-memory
`AIRunManager`, not this FastAPI/HTTP provider path
(`backend/tests/ai_automation/test_ai_harness.py:101-124`). D-8 and the
documented clear cancellation semantics therefore remain unverified.

### A-04 — High / release blocker: sync ordering improved in the mounted route, but production acceptance is not proven

The mounted route now requires a device-bound token, owner-scopes operation
receipts, serializes PostgreSQL pushes with an owner advisory transaction
lock, and starts bootstrap under repeatable-read (`backend/app/sync/api.py:35-43`,
`backend/app/sync/api.py:45-73`, `backend/app/sync/api.py:87-97`). These changes
address the earlier same-owner allocation/commit interleaving risk.

The checked-in PostgreSQL route still has no compaction watermark/reset
protocol or bootstrap page token, and its generic `patch` accepts arbitrary
neutral keys for ordinary resources. The strict typed service and its tests
are not the mounted persistence implementation (`backend/app/main.py:30-35`).
The sync tests use a fake store; CI runs Alembic against its default local
SQLite database and has no PostgreSQL service or concurrent mounted-route
test. Thus commit-order safety, bootstrap behavior, tombstones after
compaction, and production reset behavior remain release-gate evidence gaps.

### A-05 — Medium / CI regression: generated OpenAPI check is not clean in the current tree

The local checks pass 36 Python tests, compilation, 24 Rust unit tests, 13 Rust
integration tests, formatting, and clippy. The generated OpenAPI document has
63 paths and differs from `docs/openapi.json` only by the final newline:
the generator writes a newline while the checked-in file has none. Since
`.github/workflows/ci.yml:20-21` overwrites the file and then runs
`git diff --exit-code`, a clean CI run is expected to fail on this byte-only
difference. CI also lacks Python type/lint checks, dependency/security scans,
PostgreSQL integration, and dedicated attestation/cancellation security tests,
despite H-7 requiring unit/integration/type/lint and relevant security
coverage.

### Disposition and local resolvability

The implementation work for A-01 provenance binding, A-03 cancellation
propagation, A-04 mounted PostgreSQL integration/compaction tests, and A-05 CI
coverage is locally resolvable without a product decision. The OpenAPI newline
regression is also a local documentation/CI fix.

The final A-01/A-02 acceptance result cannot be established by source changes
alone: it requires a supported macOS environment, an integrity-controlled
probe/helper build, and a real authenticated compatibility run against the
installed vendor CLI. Choosing the supported macOS versions, provider
credential model, and any external backup policy remains subject to the
existing OPEN/PROPOSED decisions. Until that evidence exists, unattended
vendor execution and the overall completion gate must remain disabled.

earlier source excerpt: `apps/runtime/src/sandbox.rs:206-355` validates the

and probe executable before and after execution. This removes the previously
described unrestricted caller-selected probe path inside the runtime. It does
not close A-01: those provenance values remain local `ProbeEvidence` fields,
are not carried in the serialized `ProbeResult`/attestation, and the backend
still validates only boolean evidence at `backend/app/agents/api.py:139-147`.
The backend therefore cannot independently verify the helper/probe identity or
the `os_level_enforced` claim.

The mounted sync route also has a narrower cursor hazard in addition to the
missing production compaction/reset protocol. It releases the PostgreSQL
owner advisory lock at `await db.commit()` and only then reads the latest
`SyncChange.seq` at `backend/app/sync/api.py:71-73`. A different push can
commit between those statements, causing `server_cursor` to name a change that
was not returned in this response; a client that treats that cursor as fully
acknowledged can skip that concurrent change. Per-operation cursors remain
bound to the flushed change, but the top-level cursor is not a safe receipt for
all changes it may include. This is locally resolvable and keeps the mounted
commit-order acceptance gate open.

### A-06 — High / release blocker: HTTP AI cancellation still has a start race and a process-local control handle

The recent change correctly creates an `asyncio.Event`, passes it into the
transport and execution service, checks the persisted row between stream events,
and avoids writing `completed` after a persisted cancellation
([`backend/app/ai/api.py:144-171`](backend/app/ai/api.py:144)). It does not make
the transition into `running` conditional. A cancel request can commit
`status="cancelled"` after the initial refresh but before the stream handler's
unconditional `status="running"` commit ([`backend/app/ai/api.py:144-150`](backend/app/ai/api.py:144)); the provider call can then start after the API has reported cancellation.

The live cancellation event is held only in the module-level
`_active_cancellations` dictionary ([`backend/app/ai/api.py:22-23`](backend/app/ai/api.py:22)). A cancel request handled by another worker, or after a worker restart, sets the database state but cannot signal the active provider task. The same dictionary is also overwritten if two event streams are opened for one run. The transport does close its HTTP response when its event is set, but that is only effective when the cancel request reaches the same process and the stream has already registered its event
([`backend/app/ai/api.py:40-70`](backend/app/ai/api.py:40)).

The passing cancellation test covers the separate in-memory `AIRunManager`,
not this FastAPI/provider path ([`backend/tests/ai_automation/test_ai_harness.py:101-124`](backend/tests/ai_automation/test_ai_harness.py:101)). D-8 and the stable cancellation portion of the AI acceptance criterion remain unverified.

Local fix: claim the run with a database compare-and-set or row lock before
starting provider work, persist a cancellation generation/state, make one
stream owner per run, and use a worker-independent cancellation signal or
durable task ownership. Add an HTTP integration test with a blocking fake
provider that covers cancel-before-start, cancel-during-read, duplicate event
streams, and final `cancelled`/no-provider-work semantics.

### A-07 — High / release blocker: mounted PostgreSQL sync still has no compaction/reset protocol or resumable bootstrap cursor

The mounted route uses an owner advisory transaction lock around pushes and
computes the top-level cursor before commit ([`backend/app/sync/api.py:35-73`](backend/app/sync/api.py:35)). That addresses the earlier same-owner
allocation/commit interleaving concern for this route. The production route
still exposes only a latest cursor in `sync/status`, a bounded `pull`, and an
unpaged bootstrap that returns every current record
([`backend/app/sync/api.py:75-97`](backend/app/sync/api.py:75)). There is no
device acknowledgement table/API, compaction watermark, reset-required
response, retained-tombstone policy, or bootstrap page token. The bootstrap
cursor is encoded as `kind="bootstrap"`, while `pull` accepts only
`kind="pull"`, so the returned snapshot watermark cannot directly resume a
pull.

The richer snapshot, compaction, acknowledgement, and reset concepts exist in
the storage-agnostic protocol types ([`backend/app/sync/protocols.py:44-67`](backend/app/sync/protocols.py:44), [`backend/app/sync/models.py:106-129`](backend/app/sync/models.py:106)), but that service is not the mounted persistence implementation
([`backend/app/main.py:30-35`](backend/app/main.py:30)). The PostgreSQL test
only checks one push, replay, device binding, and one pull
([`backend/tests/test_postgres_integration.py:12-32`](backend/tests/test_postgres_integration.py:12)); it does not exercise concurrency, bootstrap boundaries, tombstones, compaction, or reset. This leaves B-3, B-4, B-5, B-8, and B-9 open against [`docs/SYNC_PROTOCOL.md:44-50`](docs/SYNC_PROTOCOL.md:44) and [`docs/SYNC_PROTOCOL.md:86-95`](docs/SYNC_PROTOCOL.md:86).

Local fix: route the mounted API through one transactional PostgreSQL sync
service, define a committed cursor/watermark and device acknowledgements,
implement stable paged bootstrap with a resumable snapshot token, and return a
typed reset response when the cursor is below the compaction watermark. Add
concurrent PostgreSQL tests for page boundaries, rollback/gaps, tombstone
retention, and stale-device reset.

### A-08 — Critical / release blocker: attestation provenance is signed but not independently trusted

The runtime now computes and serializes profile, runtime, and bundled-probe
SHA-256 digests, and checks those files before and after the local probe
([`apps/runtime/src/sandbox.rs:318-370`](apps/runtime/src/sandbox.rs:318)). The
backend only requires each digest to be a 64-character string and verifies that
the device signed the request ([`backend/app/agents/api.py:39-55`](backend/app/agents/api.py:39), [`backend/app/agents/api.py:139-147`](backend/app/agents/api.py:139)). It does not compare the digests with a trusted release manifest or enrolled helper build, verify code signing/notarization, or receive an independently established OS enforcement result. The runtime sets `os_level_enforced: true` as a local consequence of the probe path ([`apps/runtime/src/isolation.rs:125-145`](apps/runtime/src/isolation.rs:125)).

Consequently, the evidence proves that a holder of the enrolled device key
signed self-consistent claims; it does not prove that the approved helper,
probe, and Seatbelt implementation produced them. The backend can mark a grant
validated from such an envelope even though the installed helper lifecycle and
trusted release identity are absent. This remains fail-safe in the current
vendor-disabled posture, but it blocks the autonomous execution gate and F-4.

Local fix: bind the attestation to a server-registered helper/probe release
manifest and canonical profile, include an explicit verified enforcement result,
consume the challenge atomically, and reject unknown or unsigned builds. The
final evidence still requires a supported macOS build/install/signing path;
source-only tests cannot establish that external provenance.

### A-11 — High / pre-enable blocker: the runner does not bind execution to the probed vendor executable

Both local execution methods accept a caller-supplied executable and pass it to
`build_invocation` ([`apps/runtime/src/runner.rs:68-117`](apps/runtime/src/runner.rs:68)).
